# Development guide

## Setup

```bash
pip install -e ".[test]"
```

## Build

```bash
pip install . -v
```

## Test

```bash
pytest tests -v --tb=short
```

## Repository layout

- `CMakeLists.txt` — native build entrypoint
- `src/pylibhmm/_core.cpp` — nanobind module
- `src/pylibhmm/_common.h` — NumPy/libhmm conversion helpers
- `src/pylibhmm/__init__.py` — Python wrappers/validation
- `tests/` — pytest suite
- `examples/` — sample usage

## Architecture

### Build model
`_core` is a single nanobind extension module built via scikit-build-core
(the PEP 517 build backend): `pip install -e .` invokes CMake, which
compiles `src/pylibhmm/_core.cpp` and links it against libhmm's
`hmm_static`.

### Dependency resolution order
`CMakeLists.txt` prefers a local `../libhmm` checkout when
`../libhmm/CMakeLists.txt` exists (added via `add_subdirectory`); otherwise
it fetches the pinned release tag via `FetchContent`. Neither path forces
any libhmm option: both rely on libhmm's `LIBHMM_BUILD_EXAMPLES`/
`LIBHMM_BUILD_TESTS`/`LIBHMM_BUILD_TOOLS` defaulting to
`PROJECT_IS_TOP_LEVEL`, which is `OFF` under `add_subdirectory` and under
`FetchContent` alike. (The seven forced unprefixed `set(... FORCE)` lines
the `FetchContent` branch once carried were removed at the v4.3.0 bump;
v4.3.0 retired those spellings, so forcing them did nothing.) The pin
value itself lives only in `CMakeLists.txt`'s `GIT_TAG` — never restated
in docs; see PLAN.md Cross-Repo Dependencies. One real consequence: the
`FetchContent` pin is exercised only on a machine with no local
`../libhmm` checkout (CI is one), so a stale pin is caught by the
`pin-currency` canary, not by local builds — see PLAN.md Known Gaps.

### `_common.h` — NumPy ⇔ libhmm conversion
Conversions are copy-based by default: NumPy input arrays are copied
element-by-element into owned libhmm value types (`Vector`, `Matrix`,
`ObservationSet`), and libhmm outputs are copied into a freshly
heap-allocated buffer wrapped in a NumPy array via an `nb::capsule` that
frees the buffer when the array is garbage-collected — no raw pointer
aliasing persists past a single call in the common path.

The one exception is `obs_matrix_views()`, which builds non-owning
`ObservationVectorView` spans pointing directly into the input NumPy
array's buffer (zero-copy), used by the MV distributions' `fit()` /
`fit_weighted()` bindings in `_core.cpp`. This is safe only because the
views are consumed synchronously within the same bound call, while the
NumPy array argument is kept alive by the Python call frame — they are
never stored past the call. Do not extend this pattern to any binding
that would retain the views beyond the call's lifetime.

### `__init__.py` — why the Python wrapper layer exists
The raw `_core` bindings accept whatever nanobind's `ndarray` type
constraints allow (contiguity, dimensionality, dtype) but perform no
application-level validation. `__init__.py` subclasses each `_core` type
to add dtype coercion (`np.asarray(..., dtype=np.float64)`, so callers
can pass plain lists), shape/dimensionality validation with actionable
`ValueError` messages, and finite-value checks — giving callers clear
Python exceptions instead of nanobind's more generic type errors,
without requiring them to know libhmm's C++ argument constraints.

### Type stubs
`__init__.pyi` and `_core.pyi` are hand-written, not generated by a tool
(no stub-generator invocation exists in the build or CI).
`docs/DEVELOPMENT.md` lists updating them as a manual step whenever
`_core.cpp` bindings change — that instruction means manual edits, not
re-running a generator, until that changes.

## Rules for API changes

When changing `_core.cpp` bindings:

1. Update `__init__.py` if wrapper signatures change
2. Update `__init__.pyi` and `_core.pyi`
3. Add or update tests for new API behavior
4. Keep docs in `README.md` and `docs/API.md` aligned
